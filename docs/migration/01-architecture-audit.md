# Architecture Audit: BookMySpace Backend

**Date:** 2026-08-10  
**Project:** BookMySpace Rental Marketplace  
**Scope:** Current MongoDB/Mongoose architecture inventory  
**Status:** Complete — ready for Phase 2 migration planning

---

## Executive Summary

The BookMySpace backend is a Node.js + Express + TypeScript application using MongoDB Atlas via Mongoose for persistence. All database interaction is handled through Mongoose models. No Supabase code is currently in use (package installed, but zero integration). The architecture is clean, well-organized, and straightforward to migrate to Supabase PostgreSQL following the repository pattern while keeping the API identical.

**Critical findings:**
1. Five real Mongoose models exist (`User`, `Property`, `Review`, `Notification`, `Comment`). No others.
2. **No Enquiry model exists** — the `contactPropertyOwner` endpoint only logs to console; inquiries are not persisted to any database.
3. Refresh tokens are **stateless JWTs** — no database-backed revocation or rotation tracking exists today.
4. All models use MongoDB's automatic `_id` (ObjectId) and timestamps. The Postgres migration will use UUIDs and timestamp functions instead.

## Critical Discrepancies from Earlier Docs

### 1. No Enquiry Model Exists
**Found:** The older audit reports mention an "enquiries" table as if it's a real, persisted collection.

**Reality:** No Mongoose `Enquiry` model file exists in `src/models/`. The `contactPropertyOwner` endpoint (propertyController.ts:758) only logs inquiries:
```typescript
console.log(`[Inquiry Sent] Property "${property.title}" - From: ${name} (${email}) - Message: ${message}`);
```
Nothing is written to any database collection.

**Decision needed:** In Phase 2/3, should `enquiries` become a real table (to persist property inquiries going forward)? Or should it remain out of scope and `contactPropertyOwner` stay as log-only? This is a scope question, not a data-migration issue (there is no existing enquiry data to migrate).

### 2. Refresh Tokens Are Stateless JWTs
**Found:** `src/utils/jwt.ts` shows all token operations:
```typescript
export function generateRefreshToken(payload: JwtPayload): string {
  return jwt.sign(payload, env.jwtRefreshSecret, {expiresIn: env.jwtRefreshExpiresIn});
}
export function verifyRefreshToken(token: string): JwtPayload {
  return jwt.verify(token, env.jwtRefreshSecret) as JwtPayload;
}
```

**Reality:** Refresh tokens are self-contained JWTs. No database lookup, no token revocation/blacklist table, no session management. The token validation is 100% cryptographic (verify signature + expiration).

**Implication for Postgres:** A new `refresh_tokens` table could be added to support:
- Token revocation on logout
- Token rotation (old tokens invalidated on refresh)
- Session management

But this is a **new feature**, not a port of existing behavior. If added in Phase 2+, it's optional and strictly additive — the app will continue working without it.
